Question: how should the memory be managed (write, index, retrieve, rank, consolidate, forget, validate, audit), how should the expensive LLM and simulator calls be cached, how is memory evaluated, and how is it secured. ## 0. Findings

1. **Gate-accepted writes beat "store everything".** The only controlled study of memory addition and deletion for agents (Xiong et al., 2025) found that storing every execution was worse than a small fixed memory on all four agents (RegAgent success 55.48 vs 67.53; AgentDriver 32.32 vs 40.11; EHRAgent accuracy 13.05 vs 16.75; CIC-IoT 59.90 vs 71.50), and that admitting only executions confirmed by a strict evaluator was best (70.95, 51.00, 38.50, 85.40). ANTS's regression gate on deterministic simulator outcomes is exactly a strict evaluator, so the admission rule is "gate-accepted only" [read].
2. **Retrieval relevance alone is not enough; an applicability check is.** In Skill-V, semantic retrieval alone gave 71.9% success on ALFWorld, adding deterministic contract checks 89.1%, adding an LLM applicability judge 95.3%; the judge marked 29.6% of retrieved candidates "confidently inapplicable". Growth without revision was worse than a static library (acquisition-only 68.80 vs static 73.40) [read; preprint, 0 citations, text agents]. In ANTS a runnable `precondition` plus envelope check is the deterministic version of this filter.
3. **Retrieve few.** ReasoningBank: 39.0% success with no memory, 49.7% with one retrieved experience, then 46.0 / 45.5 / 44.4 with 2 / 3 / 4 (WebArena-Shopping subset, one model) [read]. Default top-k for ANTS should be 1 to 2 with a similarity floor, and k is a parameter to ablate.
4. **The pheromone ranker (similarity x decayed usage) has no direct precedent; its parts do.** Generative Agents (recency x importance x relevance, additive, min-max normalised), MemoryBank (retention e^(-t/S), S+1 on recall), ExpeL (importance count 2, +1/-1, delete at 0), ACT-R base-level activation (ln sum t^-d) and Xiong's utility-based deletion are the building blocks. None multiplies similarity by usage. A multiplicative form cannot retrieve something irrelevant just because it is popular, which is the property wanted against negative transfer. It is a design choice to ablate, not a literature result.
5. **Forgetting is the weakest capability in the benchmarks.** MemoryAgentBench: every method failed multi-hop selective forgetting (at most 28% accuracy); even o4-mini fell from 80.0 (6K context) to 14.0 (32K) on FactConsolidation multi-hop [read]. ANTS should not rely on an LLM to resolve conflicting entries; use deterministic scope, version and evidence rules.
6. **Because ANTS stores frozen code, re-verification is nearly free in tokens.** A text agent must call an LLM to check a stored skill; an ANTS skill is replayed in the simulator at about 30 s per rollout [audit] with zero model tokens. So the staleness check can be strict: replay evidence cases after any harness, asset or launcher change. A stored program depends on the harness, assets and simulator, not on the generator model; a stored constraint (prompt text) and any cached LLM reply do depend on the model.
7. **Prompt-caching tactics are worth less than call-level caching here.** In the ledger, paid completion tokens are 54.2% of paid tokens and about 71.5% of the completion tokens are reasoning in the 21 rows that log it [R]. The provider already served 45.0% of paid prompt tokens from its prefix cache [R]. At the third-party list prices found for Muse Spark 1.3 (not the Wonder model we use; unverified) a perfect prompt cache would save about 10% of cost. The levers that matter are (a) the exact call cache (21 hits already avoided 568,247 tokens), (b) fewer calls per cycle (a memory warm start), (c) reasoning-effort control if the API honours it (one developer reports it is inert; unverified).
8. **Rollout memoisation is justified by data, with a canary.** MuJoCo documents "MuJoCo simulations are deterministic" [read]; in the repo 63 of 65 repeat groups were byte-identical and the two exceptions straddled a launcher fix [audit]. Cross-machine determinism is unverified. A key must contain every input (Bazel's hermeticity rule: undeclared inputs give wrong hits [read]).
9. **Semantic caching is not a cache here.** vCache shows correct and incorrect semantic hits have highly overlapping similarity distributions and a static threshold gives no error guarantee [read]. Exact keys only for LLM replies and rollouts; "similar" reuse goes through memory, which validates before use.
10. **Poisoning needs a record to be stored; ANTS can make storage hard.** AgentPoison reports at least 80% attack success at a poison rate below 0.1% with at most 1% benign loss [read abstract]; MINJA injects through queries only (98.2% injection success, 76.8% attack success) and defeats embedding-level sanitisation and cheap prompt-level detection [read]. The 2026 defences converge on provenance and derivation lineage (MemLineage, signed entries plus a Merkle log) rather than content filtering [abstract/summary]. For ANTS: typed records, no free external text in `rule`, gate-verified admission, hash-chained audit log, signatures only when memory is shared across machines or users.

Xiong deletion rules, quoted as formulas: periodic deletion removes records not retrieved often enough in a window `[t', t]` (a fixed threshold on retrieval count); history-based deletion removes a record when it has been retrieved at least `n` times and the mean utility over those retrievals is at most `beta`: `delete(i, t) = 1[ f_t(i) > n and (1/f_t(i)) * sum_{m=1..f_t(i)} Phi(q_m, e_m) <= beta ]`; combined is the union of the two. Numbers with a strict evaluator, memory size in parentheses: RegAgent no deletion 70.95 (2938), periodic 67.65 (949), history 69.80 (2286); EHRAgent accuracy no deletion 38.67 (1012), periodic 38.59 (302), history 42.06 [read]. So periodic deletion cut memory by about 68% and 70% (computed from the table) at a loss of 3.3 and 0.1 points.

### 2.5 Cognitive science and classical selection / eviction by utility

| Source | Rule | Use for ANTS |
|---|---|---|
| **Ebbinghaus curve** (via MemoryBank) | `R = e^(-t/S)`, S grows with each recall [read via MemoryBank] | Exponential retention with spacing. Simple, but MemoryBank gives no ablation |
| **ACT-R base-level activation** (Anderson and Lebiere 1998; Anderson and Schooler 1991) [summary of a secondary chapter; primary not read] | `B_i = ln( sum_{j=1..n} t_j^(-d) )`, t_j = time since the j-th use, decay d conventionally 0.5; derived from the statistics of past occurrence (rational analysis). A secondary source reports that exponents fitted to Ebbinghaus and Wixted/Ebbesen data are about 0.1 to 0.2, so 0.5 is a convention [summary, unverified] | A power-law, usage-reinforced decay with a fat tail: old entries that were used many times persist. Candidate ranker F3 (section 3.1) |
| **Prioritised experience replay** [1511.05952](https://arxiv.org/abs/1511.05952) (4769) | `P(i) = p_i^alpha / sum_k p_k^alpha`, `p_i = |delta_i| + eps`; importance-sampling weights `w_i = (N * P(i))^(-beta)` [memory] | Utility-based selection with a correction for the bias of non-uniform sampling; the analogue for ANTS is to avoid always retrieving the same top entry (exploration) |
| **Experience replay for continual learning** [1811.11682](https://arxiv.org/abs/1811.11682) (1949); **DER** [2004.07211](https://arxiv.org/abs/2004.07211) (1549) | A small episodic memory with reservoir sampling; DER also stores logits [memory] | Small rehearsal sets are enough to limit forgetting; here "rehearsal" = the monotone gate set |

## 3. Synthesis for ANTS

### 3.1 (a) Memory lifecycle spec

**Clock.** All decay and ageing use a logical **epoch** counter `e` (one tick per gate decision across the whole store, persisted in the store), never wall-clock time, so that retrieval is a pure function of (snapshot, query) and runs are reproducible. [audit] notes that `Skill.last_used` is a wall-clock string and recommends the same.

**Record types.**

**Re-verification cost.** `k` evidence cases at about 30 s each [audit] is `k x 30 s` of simulator time and no model tokens: for k = 5, about 2.5 minutes. Tiered check: (1) AST plan gate, free; (2) evidence replay on `k` cases; (3) full gate-set replay only before using a skill as an incumbent. [G: k=5 default.]

**Audit trail.** One append-only `memory_events.jsonl`, plus SQLite as the queryable state. Event: `{seq, epoch, wall_time (informational), op, entry_id, version, before_hash, after_hash, actor (module, model id), reason, evidence_run_ids, split, memory_sha_before, memory_sha_after, prev_event_hash}`. `op` follows the survey's vocabulary: Add, Refine, Merge, Split, Prune, Rerank, plus Retrieve, Reverify, Tombstone. `memory_sha` = hash of the sorted list of `(entry_id@version, content hash)` (a Merkle root once the store is large). Each run records the `memory_sha` it started from, the query, the ranked list with scores and the entries actually injected. State can always be rebuilt by folding the events [G, event sourcing].

**Versioning and deprecation.** Skills carry `MAJOR.MINOR.PATCH` [G]: MAJOR = interface or parameter change (callers must change); MINOR = behaviour extended with no regression on the evidence set (gate-passed); PATCH = metadata or comments. A skill is marked `deprecated` for at least one epoch window before it is excluded from retrieval, and is never deleted without a request (SemVer's deprecate-before-remove rule [memory]).

### 3.2 Retrieval rankers to compare (parameters to ablate)

Pipeline: hard filters first (task scope, `split == acceptance`, status in {verified, admitted}, `precondition(current_scene)` true, harness-compatible), then similarity floor `s_min`, then a ranker over the survivors, then pack top-k within a token budget.

Let `sim_i` be the similarity of the query to entry i. For text, use BM25 from SQLite FTS5 normalised to [0,1] and structured feature overlap (object roles, failure-signature features); dense embeddings only if the user approves a model (an embedder is a dependency decision). `h_i`, `x_i` are help and hurt events with epochs `e_j`.

| Ranker | Formula | Parameters to ablate | Properties |
|---|---|---|---|
| **F1 pheromone (the paper's N13)** | `S_i = sim_i * (eps + tau_i(e))^a`, `tau_i(e) = max(0, sum_{j in help_i} exp(-lambda (e - e_j)) - beta * sum_{j in hurt_i} exp(-lambda (e - e_j)))` | `a` in {0, 0.5, 1}; `lambda` in {0, 0.05, 0.1, 0.3} per epoch (half-life `ln 2 / lambda`: infinite, 14, 7, 2.3 epochs); `eps` in {0.1, 0.5}; `beta` in {1, 2}; `s_min` in {0.2, 0.4}; k in {1, 2, 4} | Multiplicative: popularity cannot rescue an irrelevant entry. With `a = 0` it reduces to similarity only (the ablation baseline). Risk: rich-get-richer; new entries have `tau = 0` so need `eps > 0` or exploration |
| **F1b with uncertainty** | `S_i = sim_i * q_i`, `q_i = LCB_z( help_i / (help_i + hurt_i) )` (Wilson lower bound, z = 1.28), prior Beta(1,1); exploration by Thompson sampling: draw `q_i ~ Beta(1 + help_i, 1 + hurt_i)` instead of the bound | `z`, prior, greedy vs Thompson | Avoids ranking an entry first because it was used once; consistent with the Thompson sampling the planner already uses [G] |
| **F2 recency x importance x relevance** (Generative Agents) | `S_i = w_s * norm(sim_i) + w_r * rho^(e - e_access_i) + w_i * norm(imp_i)`; GA used `rho = 0.995` per game hour, `imp` from an LLM (1 to 10), all `w = 1`, min-max scaling [read] | `rho` in {0.9, 0.95, 0.99} per epoch; weights; `imp_i` := number of previously failing cases flipped to pass by the candidate that used the entry (deterministic, no LLM) | Additive: an irrelevant but recent or important entry can outrank a relevant one. Recency counts access, not usefulness |
| **F3 ACT-R activation** | `A_i = ln( sum_{j=1..n_i} (e - e_j + 1)^(-d) ) + w_s * sim_i` (+ optional noise), `e_j` = epochs of helpful uses and of creation; retrieve if `A_i > tau_r` | `d` in {0.2, 0.5}; `w_s`; `tau_r` | Power-law forgetting: often-used old entries persist; additive in similarity; the `d` value is a convention [summary] |

Expected ordering [G]: F1 or F1b best on negative-transfer-prone stores (many tasks), all rankers within noise at tens of entries. The offline retrieval benchmark in section 6 is how to find out cheaply.

**Credit assignment (what counts as "help").** The gate gives one bit per candidate, but all retrieved entries are in the prompt together. Cheap, deterministic rules [G]:
- help(i) when a candidate generated with entry i in the prompt is accepted by the gate and the case that triggered or retrieved i now passes;
- hurt(i) when a candidate generated with i in the prompt fails the gate on a case the incumbent passed, and i was the only memory item added relative to the previous attempt (otherwise log as unattributed);
- optional leave-one-out probe on a budget: regenerate once without i; expensive (one more call), reserve for entries about to be deprecated or promoted.
This is the weakest part of the design: no paper in section 2 solves credit for prompt-composed memory (Xiong et al. use ground-truth utility; Memento learns a retrieval policy from reward).

### 3.3 Write, dedup, consolidate

- **Admission (write rule).** State machine `proposed -> admitted -> verified -> deprecated`. `admitted` = the regression gate accepted the candidate on acceptance-set cases (the equivalent of Xiong's strict evaluator, the best of five addition policies there [read]; Skill-V's non-regression-on-replay [read]). `verified` = a second run of the evidence cases under the current harness fingerprint reproduces the outcomes (also catches non-determinism). Never admit from a self-report, from a held-out case, or from an LLM judge alone (AWM and ReasoningBank rely on self-judged success; Xiong shows coarse automatic judges can be worse than a fixed memory [read]).
- **Consolidation without an LLM.** Mem0 and A-MEM use an LLM to decide ADD / UPDATE / DELETE / NOOP and to rewrite old notes; each decision costs tokens, is non-deterministic and was not validated against a ground truth in those papers. For ANTS use deterministic keys (structured signature features, `code_sha`, normalised AST) and the behavioural-equivalence test above. An LLM may propose a merge as a candidate, but a merge is admitted only if the merged entry passes the union of both evidence sets (the Skill-V non-regression rule applied to merge).
- **Summarise at write time, not at read time.** Store a short rule (target at most 60 tokens) next to the full evidence; the prompt gets only the rule and an id (section 4.4). Distilling to strategy items is what ReasoningBank does [read].
- **Conflicting entries.** Do not delete the loser: set `valid_to_epoch` (Zep's invalidation by timestamp rather than deletion [read]) and keep `superseded_by`.

### 3.4 Forgetting and deprecation

Retrieval priority fades through `tau` or `A_i` above. Removal from the retrievable set (deprecation) uses a separate, more conservative rule, because over-pruning erases rare essential knowledge [read, survey] and because Smyth and Keane's result is that deleting pivotal cases loses competence permanently [summary]:

```
value_i(e)  = q_i * exp(-lambda_f * (e - e_last_help_i))
deprecate_i = (not pivotal_i) and (
                 [ n_ret_i >= n_min  and  mean_util_i <= beta_u ]        # Xiong history-based rule
              or [ value_i(e) < v_min and age_i > grace ]                # fade rule
              or [ failed_reverify_i ] )                                  # evidence replay failed
pivotal_i   = removing i reduces |union of case_keys passed by verified entries of the same scope|
```

Parameters to ablate: `n_min` in {3, 5}, `beta_u` in {0.3, 0.5} (utility = fraction of retrievals followed by gate acceptance), `lambda_f`, `v_min`, `grace` in epochs. `pivotal` is computable because ANTS stores per-case outcomes for every entry (the competence footprint of Smyth and Keane, adapted [G]). A deprecated entry stays in the store, is excluded from retrieval, and is purged only on request. Evidence for the size effect: periodic deletion shrank memory about 68 to 70% at 0.1 to 3.3 points cost [read, Xiong, computed], so deprecation matters for cost more than for accuracy.

### 3.5 Anchoring to the paper

The paper's N13 ("top-k retrieval by embedding similarity weighted by a usage score ('pheromone') that decays over time and is reinforced when a program contributes to an accepted rewrite") is F1 with `tau` as the pheromone; "contributes to an accepted rewrite" is the help rule above. C11 (what memory holds in a one-task hackathon run) is answered in 4.6.

### 5.2 Keys and invalidation (hermetic keys)

Principle from Bazel and Build Systems a la Carte: the key must contain **every** input that can change the output; anything left out silently produces stale hits, and a poisoned entry is served to everyone with the key [read]. Constructive traces store the result next to the hashes of the inputs; early cutoff reuses downstream results when an upstream recomputation yields an identical output hash [read].

```
llm_key     = H(schema, endpoint host, model alias, response-model snapshot id (if known), request dict
                (messages, temperature, max_tokens, every other param sent), sample_index, cache_epoch)
rollout_key = H(schema, sha(program bytes), case_key (suite, task, seed, init mode, layout_fp),
                canonical scene spec (incl. actuation seed, scale, ablate flags), max_steps, camera size,
                harness {aspire commit + diff hash if dirty, dependency_lock_sha256, launcher_sha256,
                providers, SAM 3 checkpoint hash, LIBERO assets hash, MuJoCo version}, perturbations_version)
extract_key = H(clip bytes, marker size, setup yaml, extractor git sha)
```

The detailed fields and the proposed fixes to `llm.py` and `rollout.py` are in [memory-audit-codebase.md](memory-audit-codebase.md) section 4; this note adds three rules from the build-system literature: (1) **write access to one process** (a single writer thread/process per store, readers read-only; Bazel's advice for shared caches); (2) **store the request next to the response** and re-hash on read so the entry audits itself; (3) **early cutoff**: if only the diagnoser version changes but a diagnosis text is byte-identical, downstream prompts keep their keys and their cached LLM replies.

Invalidation: a cache entry is never edited; a changed input yields a new key. Namespaces (`cache_epoch`, split) allow bulk invalidation. Rollout entries from the infrastructure error class (harness error, subprocess timeout, EGL "invalid depth" under GPU contention) are not stored. Sentinel: each cycle re-run one cached case; a mismatch quarantines the fingerprint.

### 5.4 Prompt layout for the program-writing call (stable prefix, variable suffix)

Order, most stable first [G, grounded in the OpenAI/Anthropic/Lumer guidance read above]:
1. System rules, API reference, example program (about 5.6k tokens today; versioned as `prompt_version`).
2. Task text, DemoSpec summary (identical for all samples of a task, so shared across cycles and, for the demo arm, across samples). The no-demo arm should share block 1 with the demo arm and omit block 2's demo part; the arms then share the longest possible prefix.
3. Retrieved memory block (frozen for the generator session, entries sorted by `entry_id`, not by score, so a score change does not alter bytes).
4. Constraints of this cycle, then failure feedback and diff context (append-only).
Rules: serialise JSON with sorted keys and fixed float formatting; no timestamps, run ids, UUIDs or file paths in blocks 1 to 3; repair turns append, never rewrite earlier turns; keep the retrieval at session start, not per turn; run all samples of one arm close together in time (the elapsed-time pattern above suggests a TTL of minutes); report `cached_tokens / prompt_tokens` in the ledger per tag so the effect is visible. Provider-specific notes if a reference arm uses another API: Anthropic needs explicit `cache_control` breakpoints (up to 4), reads cost 0.1x, a 5-minute write 1.25x, so a prefix pays off after one reuse; the minimum length is 512 to 4,096 tokens depending on the model; OpenAI is automatic from 1,024 tokens.

## 6. (d) Evaluation design

**Budget reality.** At the HANDOFF price a $15 cap is about 1.1M tokens; at 100k to 300k tokens per hardening run [G, extrapolated from 55k to 106k per Experiment 01 sample] that is roughly 4 to 11 end-to-end runs in total. End-to-end run-level replication per arm is therefore not affordable; the powered unit is the **case** (paired, 50 held-out cases per arm), and everything else is evaluated **offline on logged and cached data** at no model cost. Whether the cap or the price is right is unreconciled (section 5.3); ask the user.

**Offline retrieval benchmark (no new LLM calls).** Build from the logs: queries = (failure signature features, scene features, task) of each cycle; positives = entries whose inclusion preceded a gate acceptance that fixed the case, plus leave-one-task-out positives across T0/T1/T2. Compare rankers F1, F1b, F2, F3 and similarity only, with the parameter grids of section 3.2, on precision@k, recall@k and MRR. This is a cheap proxy; its labels come from few events, so report counts, not only rates.

**End-to-end arms** (same seeds, same acceptance and held-out split, frozen snapshot for held-out):

| Arm | Change | Question |
|---|---|---|
| A0 | Memory off | Baseline (the paper's "ANTS without memory") |
| A1 | Memory on: F1, k = 2, decay off (`lambda = 0`), gate admission | Does memory help at all |
| A2 | A1 with decay on (`lambda = 0.1`) | Does forgetting help or hurt |
| A3 | A1 with k in {1, 4} | Retrieval noise (ReasoningBank-style k curve) |
| A4 | Ranker F2 / F3 / similarity only | Does the usage weighting matter |
| A5 | Admission: add-all vs gate-accepted vs gate + replay-verified | Negative transfer (Xiong) |
| A6 | Re-verification off vs on, after a deliberate harness/asset change (e.g. the scaled-scene tolerance fix) | Stale-hit rate and its cost |
| A7 | Poison test: inject N crafted entries (instruction-like text, wrong rules) | Security (section 7) |

**Metrics.**

| Metric | Definition | Notes |
|---|---|---|
| tokens-to-robust | Cumulative paid tokens until the stop rule fires or the incumbent passes M acceptance cases | Counts reasoning tokens; report cycles-to-robust too |
| held-out success | Passed / 50 held-out cases of the final policy, with a Wilson 95% interval | Never used for tuning |
| regression count | Cases passed by the incumbent and failed by the accepted successor, on acceptance (must be 0 by construction) and on held-out (a check on over-fitting) | |
| retrieval precision@k | Fraction of injected entries that are positives by the rule above or judged applicable by their precondition | Report with counts |
| help rate / hurt rate | Gate-accepted vs gate-rejected candidates among those that had an entry in the prompt | Usage reported separately from utility |
| stale-hit rate | Retrieved entries failing re-verification / retrieved entries | With zero events the 95% upper bound is about 3/n (rule of three, n=50 gives 0.06) |
| memory size and trajectory | Entries, tokens, operator velocities (Add, Refine, Merge, Prune) per epoch | The survey's reporting checklist |
| cache hit rates and cost | Hits, avoided tokens and seconds, `cached_tokens` share, tokens per cycle | |

**Sample sizes and intervals** (Wilson 95%, computed):

| Observed | Interval |
|---|---|
| 5/5 (Experiment 01 evaluation) | [0.566, 1.00] |
| 40/50 | [0.67, 0.888] |
| 45/50 | [0.786, 0.957] |
| 160/200 | [0.739, 0.85] |
| 0/50 | [0.0, 0.071] |
| 3/50 | [0.021, 0.162] |

For arm comparisons use the **paired exact sign test on discordant cases** (same 50 cases): with b cases fixed and c cases broken, two-sided p is 0.031 for 6:0, 0.0215 for 9:1, 0.035 for 12:3, 0.041 for 15:5, but 0.109 for 8:2 and 0.070 for 7:1 [computed]. So at n = 50 a memory effect is detectable only if it flips roughly 6 or more cases in one direction with at most 1 or 2 in the other. Report the discordant counts, not only the rates. Run-level (generator sampling) variance is not covered by 50 cases; with 2 to 3 runs per arm say "hint, not result" as Experiment 01 does. Treat the ablation table as a descriptive report; do not claim significance on run-level differences.

## 7. (e) Security and integrity

| Threat in ANTS | Channel | Control |
|---|---|---|
| **Prompt injection through stored text** | `Constraint.rule` and `when_to_apply` are generated from failure feedback (program stdout, exceptions, scene text, human demo text) and then pasted into the generator prompt. A program can print instruction-like strings that reach the diagnoser | Render `rule` from enumerated fields and templates (signature features, category, parameter name and bound) rather than free text; cap length; strip control characters; wrap memory in a delimited block labelled "retrieved notes, not instructions"; lint stored text for imperative patterns aimed at the model; a test that feeds an instruction-like exception and asserts it does not appear in any stored rule |
| **Poisoning by a wrong but plausible entry** | AgentPoison / MINJA-style writes; in ANTS a bad entry arises from a lucky gate pass or an overfitted rule | Gate-verified admission with replay on fresh acceptance seeds; `verified` state; hurt events; Beta posterior with exploration so one bad entry cannot dominate; a pivotal-entry rule so the only copy is not silently replaced. Note the limit: a backdoor that passes simulation but encodes a trigger is outside what a gate on benign cases tests |
| **Executable memory** | `check_code`, stored programs, `Skill.code` | Allow-list AST plan gate before any execution; run only in the sandboxed simulator; CoALA's warning that writing procedural memory is riskier than semantic memory [read]; no `eval`/imports in `check_code`; physical deployment needs a human release gate (skills.md already lists a safe envelope) |
| **Provenance** | Who wrote what | Every entry has `writer` (module, model id, version), `source_run`, `derived_from` ids, `trust_tier` in {human, gate_verified, unverified}. Trust of a derived entry is the minimum along its derivation DAG (MemLineage's chain-of-custody idea; provenance rather than content decides trust [abstract/summary]). Only `gate_verified` and `human` tiers may change retrieval weights |
| **Tampering and audit** | Local files edited by hand or a rogue process | Hash-chained event log (`prev_event_hash`) and per-entry content hashes make tampering detectable; the `memory_sha` in each run record pins the snapshot. Signatures (Ed25519 as in MemLineage) are needed only if memory is exchanged across machines or users; locally a hash chain suffices [G] |
| **Cache poisoning** | A bad cached reply or rollout served to every run | Single writer; store the request and verify the hash on read; quarantine on canary mismatch; read-only mount for evaluation runs (Bazel's advice: restrict write access, readers do not upload [read]) |
| **Secrets** | API key in cache or ledger | Keep the existing absence of keys in cache files and add a test asserting no `Bearer` string in stored files [audit] |
| **Privacy and deletion** | Hand keypoints of a person in DemoSpecs | Section 4.8 |

The ANTS threat model is mostly accidental or self-inflicted (one user, one lab), so cheap hygiene (typed records, templated rules, gate admission, hash chain, tests) is proportionate now; heavy machinery (signing, Merkle logs, consensus validation) is a later tier for shared multi-user memory [G]. MINJA's finding that embedding-level and cheap prompt-level defences fail [read] is the reason not to rely on content filtering alone.

## 8. (f) What the literature does not settle (so these recommendations are guesses)

1. **The multiplicative similarity x usage ranker.** No paper tests it. Generative Agents, ACT-R and MemoryBank are additive or pure-usage; ExpeL and Xiong use usage only for deletion. Choosing F1 is a design bet; the offline benchmark and ablation A4 are the test.
2. **Decay form and rate.** MemoryBank reports no ablation of its forgetting; the exponent in ACT-R is a convention (a secondary source reports 0.1 to 0.2 on other data); Generative Agents' 0.995 per game hour is not transferable to epochs. All `lambda`, `d`, `rho` defaults here are guesses.
3. **Credit assignment for prompt-composed memory.** Section 3.2's help/hurt rules are heuristics; no cited paper offers a cheap, unbiased estimator.
4. **Whether memory helps robot-program synthesis.** The evidence is on text agents (ALFWorld, WebShop, web navigation, QA, EHR); the nearest robot work (ASPIRE skill library, RAPID, ARCHITECT, Harness VLA) is only summarised in `module-radar.md` and is not memory-ablation evidence. Skill-V has 0 citations and no code that I saw.
5. **Top-k.** The k = 1 optimum is one subset, one model.
6. **Staleness rates.** No study measures how fast stored skills go stale after a model, harness or asset change; the survey calls maintenance schedules "engineering defaults". The re-verification triggers here are rules of thumb, justified only by near-zero token cost.
7. **Poisoning of gate-verified, code-valued memory.** Attacks and defences studied are on text memories; MINJA shows that detection prompts either miss or over-flag. Whether a simulator gate is a sufficient filter is untested.
8. **Meta API caching.** TTL, minimum length, price and the effect of reasoning-effort parameters are undocumented in what I found; the elapsed-time pattern in the ledger is confounded.
9. **Cross-machine simulator determinism** and whether the GPU, EGL driver or SAM 3 introduce nondeterminism are unmeasured beyond one machine.
10. **No benchmark for embodied code-skill memory.** LongMemEval, LoCoMo and MemoryAgentBench are conversational; ANTS must build a small one, which is why the evaluation uses cached logs.
11. **Scaling thresholds** (JSON to SQLite to vector index) are driven by concurrency and by arithmetic here, not by a measurement of ANTS stores.
