What cuRobo sees, and why plans fail

Experiment 07 (cuRobo planning on the SAM 3 depth cloud). Two replays of real programs: a failed one and a successful one. Robot base frame, metres; the spheres are cuRobo's 61 collision spheres.

What happens

  1. cuRobo only sees a depth cloud. Each move_to_pose becomes a plan: the service gets the points of the current depth image (robot pixels removed with SAM 3 masks), carves out points within 2 cm of the robot at its start pose, and asks for a path that keeps the robot's spheres clear of every remaining point.
  2. The bowl in the gripper is an obstacle. The bowl is not attached to the robot, and none of the 43 programs of experiments 06 to 08 passes it as target_point_cloud, so its depth points stay in the cloud. The red points in the failed run sit 10 to 18 cm under the hand flange (median 14 cm), where the held bowl hangs. Any goal that lowers the hand moves its spheres into those points, so cuRobo answers goal state infeasible (scene_collision) before it tries any path. The program retries the same goal and fails again.
  3. A path without collision checks would also collide. The orange line is the straight joint interpolation to the goal; it touches the same points. In the successful run the first 11 plans have goals clear of the cloud (one has a single point inside a sphere), so the green planned path exists with 0 colliding spheres. The same run also has 9 failed plans at the end (11 and 6 cloud points inside the goal spheres); its program finished the task anyway, and I did not check which part of the program those moves belonged to.
  4. Across experiments 06 to 08 (43 rollouts): 142 of the 182 failed move_to_pose calls were "goal state infeasible (scene_collision)", 22 other cuRobo refusals, 10 timeouts (final waypoint did not converge within 120 steps; error 0.14 to 0.3 rad) and 8 "episode ended". Source: trace/calls/*move-to-pose/output.json of the 9 runs.
Caveat: my collision test is a replay (sphere against cloud point, 1.5 cm clearance, same 2 cm carve); cuRobo's own check is voxelised and can differ by a few millimetres. The cause of the 10 timeouts is not investigated here.
